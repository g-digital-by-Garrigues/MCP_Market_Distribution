# ADR 0008: n8n adapter — REST-direct execution model

**Status:** Accepted  
**Date:** 2026-05-28  
**Story:** Epic 12 Story 12.1 spike  
**Supersedes:** implicit architecture in `templates/n8n-adapter/node.ts.hbs` (v0)

---

## Context

Epic 11 Story 11.6 (pre-submission linter validation) found that all 3 published n8n adapter packages (`@g-digital/n8n-nodes-*`) fail `@n8n/scan-community-package` with 50+ ESLint violations. The root cause is architectural: the current adapter bundles the full MCP server and spawns it as a subprocess at n8n node execution time:

```
CURRENT: n8n node → spawn child_process → MCP server (stdio) → REST API
```

This architecture violates n8n Cloud's security policy:

| Violation class | Count (per package) | Examples |
|---|---|---|
| `no-restricted-imports` | ~10 | `require('fs')`, `require('path')`, `require('child_process')`, `require('stream')` |
| `no-restricted-globals` | ~45 | `process`, `global`, `globalThis`, `setTimeout`, `clearTimeout`, `__dirname` |
| `valid-peer-dependencies` | 1 | `n8n-workflow` must be `"*"`, not `">=1.79.0"` |

All violations originate from the bundled MCP SDK + server — not from the hand-authored n8n node code. The violations cannot be fixed by changing the node code; they require eliminating the bundled subprocess entirely.

**Design constraint (Hugo Alonso, 2026-05-28):** n8n node operations must map 1:1 to MCP tools. When the underlying API changes and `@suite/generator` regenerates the MCP tools, the n8n node follows automatically. No separate hand-maintained manifest.

---

## Decision

Replace the current subprocess architecture with a **REST-direct** architecture:

```
NEW: n8n node → fetch() → REST API directly (no MCP subprocess)
```

The generated n8n node will:

1. **Use only `fetch()`** for all HTTP calls — no Node.js internals, no npm dependencies beyond `n8n-workflow` peer.
2. **Obtain a Bearer token** by calling the API's auth endpoint directly via `fetch()` (same call the MCP's auth adapter makes — both are pure `fetch()`).
3. **Derive the REST call for each operation from the generated MCP source** — specifically the `// Sourced from operation:` comment in each `src/tools/<tool_name>.ts` file.

### Tool→Endpoint mapping source

**Every `src/tools/<tool_name>.ts` file generated by `@suite/generator` has a machine-readable header comment:**

```typescript
// Auto-generated by @suite/generator. Do not edit.
// Sourced from operation: ListCaseFilesController_run (GET /users/{userId}/case-files)
import { listCaseFilesControllerRun } from "../api/sdk.gen.js";
```

The extraction regex is:
```
/\/\/ Sourced from operation: \S+ \((\w+) ([^)]+)\)/
```
→ `group(1)` = HTTP method (`GET`), `group(2)` = URL template (`/users/{userId}/case-files`)

**Coverage (confirmed on gocertius, 2026-05-28):** 33 of 38 tools have this comment (all auto-generated ones). 5 are custom/handwritten tools (`dossier_certify`, `dossier_evidence_link`, `chat_certificate_get`, `session_info`, `session_login`) — these use the SDK function name as fallback and will need manual URL annotation in a follow-up.

**Path parameters:** URL templates like `/case-files/{caseFileId}` use parameter names that match the tool's input schema field names exactly (confirmed from `src/api/sdk.gen.ts` Data types). No additional mapping needed.

### Authentication model

**GoCertius + EAD Enterprise Suite** use an email/password or OIDC refresh-token flow that issues a Bearer JWT. The n8n node calls the auth endpoint directly:

```typescript
// Email/password flow (from src/core/auth/email-password.ts):
const loginRes = await fetch(`${baseUrl}/session`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, password }),
});
const { jwt } = await loginRes.json();
// Then: Authorization: Bearer <jwt>
```

This is pure `fetch()` — zero Node.js internals. The n8n credential class stores `baseUrl`, `email`, `password`. The node refreshes the token per-execution (simple; JWT TTL is typically 1h; acceptable for n8n execution cadence).

**Option evaluated: `httpRequestWithAuthentication()`** — n8n's built-in OAuth2 helper. Verdict: not the right fit for this auth model. The GoCertius/EAD auth is a custom session endpoint (`POST /session`), not a standard OAuth2 token endpoint (`grant_type=password` or `grant_type=refresh_token` per RFC 6749). `httpRequestWithAuthentication()` expects a configured OAuth2 credential type with specific token URL and grant type; mapping our custom session endpoint would require a credential class that misrepresents the flow. **Decision: use manual `fetch()` for token acquisition.** This is also what the MCP itself does (same `fetch()` call in `email-password.ts`).

**ead-factory** uses Okta `client_credentials` grant:

```typescript
// POST OKTA_TOKEN_URL with grant_type=client_credentials
const params = new URLSearchParams({ grant_type: 'client_credentials',
  client_id, client_secret, scope });
const res = await fetch(tokenUrl, {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: params.toString(),
});
```

This is also pure `fetch()` — the Okta token endpoint is standard and `URLSearchParams` is available in n8n Cloud. The n8n credential class stores `tokenUrl`, `clientId`, `clientSecret`, `scope`, `apiBaseUrl`, `signatureApiBaseUrl`.

**ead-factory fallback (Hugo confirmed 2026-05-28):** if the automatic token fetch has any UX issues (e.g., users struggle with Okta credentials), a `bearerToken` field can be added to the credential class where the user pastes a pre-obtained token. This is Story 12.5's decision to make.

### `peerDependencies.n8n-workflow` fix

Change `">=1.79.0"` → `"*"` in `templates/n8n-adapter/package.json.hbs`. Required by the linter's `valid-peer-dependencies` rule. One-line fix in Story 12.2.

## Reference implementation

**Confirmed working (2026-05-28):** a hand-authored `GocertiusCaseFileList` node implementing `GET /users/{userId}/case-files` using only `fetch()` passes `@n8n/scan-community-package` ESLint analysis with **zero errors**:

```
passed: true  ✅ ZERO ESLint ERRORS
```

Key implementation pattern validated:
- `INodeType` with `async execute(this: IExecuteFunctions)`
- No imports outside `n8n-workflow`
- `fetch()` for auth + API calls
- Bearer token obtained via `POST /session` (same call as the MCP)
- Path parameters interpolated with `encodeURIComponent()`
- Query params via `URL` + `searchParams`

The reference implementation is at `/tmp/n8n-ref-impl/` (ephemeral, not committed — Story 12.2 will produce the production template).

## Consequences

**Positive:**
- Zero Node.js internal usage → passes `@n8n/scan-community-package` → unblocks n8n Verified Community Node submission (Epic 11 Stories 11.6-11.9).
- Architecture is simpler: no bundled server, no subprocess lifecycle, no credential bleed risk.
- Token acquisition is explicit and auditable.
- The mapping source (`// Sourced from operation:` comment) auto-updates when `@suite/generator` regenerates the MCP tools — Hugo's design constraint satisfied.
- `fetch()` is a web standard; no version pinning needed.

**Negative / tradeoffs:**
- Token is fetched per-execution (no cross-execution cache). For high-frequency workflows, this adds one HTTP roundtrip per workflow run. Acceptable given n8n's execution model and JWT TTL (~1h).
- 5 custom/handwritten tools (dossier_certify etc.) need manual URL annotation until `@suite/generator` is updated to add the `// Sourced from` comment to custom tools. Story 12.2 will document these as `// n8n-url: METHOD /path` overrides.
- `httpRequestWithAuthentication()` is NOT used → credential type does not get n8n's built-in OAuth2 token refresh. Acceptable for the current auth model (manual `fetch()` is reliable and equivalent).

**Impact on Epic 11:**
- Stories 11.6, 11.7, 11.8, 11.9 unblock after Epic 12 Stories 12.2-12.4 ship.
