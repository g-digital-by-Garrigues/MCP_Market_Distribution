# ADR 0003 — Slash-command dispatch authorized for `write` access or higher

**Status:** accepted
**Date:** 2026-05-26

## Context

The `retry-dispatch` workflow ([`.github/workflows/retry-dispatch.yml`](../../.github/workflows/retry-dispatch.yml)) lets engineers re-run failed publish steps by posting `/retry-publish` commands on release PRs. Each invocation triggers `publish.yml` — one of our most CI-expensive workflows (multi-track gates, MCPB bundle build, multiple registry publishes, ~25+ jobs per MCP).

Without an author validation policy, any commenter on a public release PR could burn CI minutes from a drive-by comment. We need a line that filters dispatchers from spectators.

Options considered:

| Option | Pros | Cons |
|---|---|---|
| **Anyone with `triage`+** | Includes reviewers without push access | Triage users can label/close PRs but not push code → they can't tag a release either, so why let them retry? |
| **Anyone with `write`+** | Aligns with "if you could push a tag, you can dispatch a retry" | Excludes triage reviewers |
| **Admin only** | Safest | Friction — most engineers with push rights would now be locked out |
| **Allowlist of specific GitHub logins** | Tightest control | Manual maintenance, breaks for org members not in the list |

The principle that resolved it: **the slash-command isn't a privilege escalation — it's a UX shortcut for people who already have the underlying authority.** Anyone with push access could just push a `v*` tag and trigger the same workflow. Restricting to `write+` means the slash-command set matches the existing publish-trigger set; we don't widen the surface, we just reduce friction for people already authorized.

## Decision

The retry-dispatch workflow authorizes the GitHub collaborator roles **`admin`**, **`maintain`**, **`write`** to dispatch slash-commands. Everything else (`triage`, `read`, `none`, or any future role we don't recognize) is rejected with a polite reply citing this policy.

The decision is encoded as policy-as-code in [`src/slash-command/validate-author.ts`](../../src/slash-command/validate-author.ts) — a pure TypeScript function with 15 unit tests, invoked from the workflow via `pnpm tsx -e`. The rejection reply text is generated by the same function (single source of truth); the runbook at [`docs/runbooks/slash-command-policy.md`](../runbooks/slash-command-policy.md) documents the rationale and edge cases for human readers.

**Authorization check uses `repos.getCollaboratorPermissionLevel`**, not `author_association`. The latter is unreliable for org members not explicitly added to the repo's contributor list (they may show as `MEMBER` despite having no role).

**Fail-closed default:** an unknown role string (e.g. a hypothetical new GitHub role we don't know about) is treated as `none` and rejected. Validate-author.ts normalizes the input to a known role enum.

## Consequences

**Wins:**
- The slash-command authorization set perfectly mirrors "who can push a tag" — no new privilege boundary to maintain.
- Policy-as-code in TypeScript is unit-testable; the inline-YAML predecessor was not.
- Adding a new role to the authorized set is a one-line change (update `AUTHORIZED_ROLES` in `validate-author.ts`) — the tests, rejection message, and runbook stay in sync automatically because they all read from the same module.

**Trade-offs:**
- Triage reviewers (label/close issues, no push) cannot dispatch retries. This is intentional — they couldn't push a release tag either.
- Bot accounts need their installation granted `write` on the source MCP repo. Lower than admin but still a coordinated grant; doesn't fall out of "anyone in the org".
- The validation makes one GitHub API call per slash-command (`getCollaboratorPermissionLevel`). At our volume this is negligible; for a pipeline operating at GitHub Actions scale it would matter.

**Why fail-closed:**
- A new GitHub role we don't know about might or might not deserve dispatch rights. Treating unknown as `none` means we don't accidentally grant rights via inaction. Adding the new role to `AUTHORIZED_ROLES` is a deliberate decision that can be reviewed in a PR.
